# T1.1: Catálogo de cuentas jerárquico

## Objetivo
Registrar y mantener el catálogo de cuentas del banco como un árbol padre-hijo de profundidad variable (regla 7 de CLAUDE.md), listo para que los asientos (T1.3) solo se registren en cuentas de detalle y para que cada cuenta indique si exige centro de costo (regla 3).

## Modelo `contabilidad.Cuenta`
| Campo | Descripción |
|---|---|
| `codigo` | Solo dígitos, único, máx. 20. El código de una subcuenta **empieza con el código de su padre** y es más largo (p. ej. `5` → `52` → `5201` → `520101`). |
| `nombre` | Nombre de la cuenta. |
| `padre` | Cuenta padre (vacío en las cuentas raíz). `PROTECT`. |
| `nivel` | 1 en la raíz; nivel del padre + 1. Calculado. |
| `tipo` | `ACTIVO`, `PASIVO`, `PATRIMONIO`, `INGRESO`, `GASTO`, `ORDEN` (cuentas de orden y contingentes). Las subcuentas **heredan el tipo** de la raíz. |
| `naturaleza` | `DEUDORA` / `ACREEDORA`. Por defecto según el tipo (Activo y Gasto: deudora; Pasivo, Patrimonio e Ingreso: acreedora; Orden: deudora); se puede cambiar para cuentas complementarias (p. ej. depreciación acumulada, estimaciones). |
| `acepta_movimientos` | `True` = cuenta de detalle (imputable); `False` = cuenta de agrupación. |
| `exenta_centro_costo` | Solo permitido en cuentas de balance (Activo, Pasivo, Patrimonio, Orden). Las de Ingreso y Gasto **siempre** exigen centro de costo. |
| `activa` | Las cuentas no se borran si tienen uso: se desactivan. |
| `creado_por/en`, `modificado_por/en` | Usuario y marca de tiempo (regla 5). |

Restricciones en **base de datos**: código único, valores válidos de tipo y naturaleza, `nivel >= 1`, `exenta_centro_costo` solo en tipos de balance. (No hay ciclos posibles porque el padre no se modifica después de creada la cuenta.)

## Reglas (en `contabilidad/services.py`)
1. El padre debe existir y estar activo; el código del hijo empieza con el del padre y es más largo.
2. Una cuenta que **acepta movimientos no puede tener subcuentas**: para agregar subcuentas, primero se marca como de agrupación. Una cuenta con subcuentas no se puede marcar como de detalle.
3. `codigo`, `padre` y `tipo` **no se modifican** después de creada la cuenta (preserva la historia). Se modifican: nombre, naturaleza, acepta movimientos, exenta de centro de costo, activa.
4. No se desactiva una cuenta con subcuentas activas, ni se activa una subcuenta de un padre inactivo.
5. Solo se elimina una cuenta sin subcuentas. (Cuando existan asientos, T1.3 agregará: ni con movimientos.)
6. Cada alta, cambio y baja queda en la bitácora con valor anterior y nuevo (entidad `cuenta`).

## Permisos
- Consultar: cualquier usuario autenticado.
- Crear, modificar, eliminar: **Contador** (y superusuario).

## API
| Método | Ruta | Descripción |
|---|---|---|
| GET | `/api/cuentas/` | Lista paginada; filtros `tipo`, `activa`, `acepta_movimientos`, `q` (código o nombre) |
| GET | `/api/cuentas/arbol/` | Catálogo completo anidado (sin paginar) |
| POST | `/api/cuentas/` | Crear |
| GET / PATCH / DELETE | `/api/cuentas/{id}/` | Detalle, modificar, eliminar |

Los errores de reglas de negocio responden 400 con mensaje en español.

## Catálogo base
Comando `cargar_catalogo_base --usuario <username>`: carga un catálogo bancario **de ejemplo simplificado** (fondos disponibles, inversiones, cartera de préstamos, depósitos, patrimonio, ingresos y gastos de intermediación y de operación, cuentas de orden). Es idempotente: no duplica cuentas existentes. No pretende ser el catálogo oficial regulatorio.

## Frontend
Página **Catálogo de cuentas** (menú, todos los roles): árbol con expandir/contraer, búsqueda por código o nombre y filtro por tipo. El Contador ve botones para nueva cuenta raíz, agregar subcuenta, editar, activar/desactivar y eliminar (formulario en ventana modal, con los errores del backend).

## Pruebas (`manage.py test contabilidad`)
Jerarquía y nivel, herencia de tipo, prefijo del código, código duplicado, padre de detalle, padre inactivo, campos inmutables, activar/desactivar, eliminar con hijos, exención de centro de costo (servicio y constraint de BD), permisos por rol, bitácora, árbol, comando de carga idempotente.
