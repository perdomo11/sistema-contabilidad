# T0.2: Autenticación JWT, roles y bitácora de auditoría

## Objetivo
Proteger la API con JWT, definir los roles del sistema y registrar en una bitácora inmutable las acciones sensibles (quién, qué, cuándo, valor anterior/nuevo). Base: CLAUDE.md (reglas 5 y 9) y documento base, sección 2.x ("control de acceso basado en roles, respaldos periódicos verificables y bitácoras de auditoría").

## Decisiones de diseño
- **Usuario:** se usa el `User` estándar de Django (ya migrado en T0.1). Los **roles son grupos de Django** creados por migración de datos; un usuario puede tener más de un rol. Los datos propios de cada rol (p. ej. el centro de costo de un Jefe de área) se agregarán cuando exista el módulo correspondiente (T2.1), no ahora.
- **Roles:** `Contador`, `Tesorero`, `Jefe de área`, `Auditor`. El **superusuario** administra usuarios y roles desde `/admin/` y tiene todos los permisos.
- **JWT:** `djangorestframework-simplejwt`. Access de 30 min y refresh de 8 h (configurables en `.env`), rotación de refresh con lista negra; el logout invalida el refresh.
- **Por defecto toda la API exige autenticación**; `/api/health/` y el login son públicos.
- **Bitácora:** modelo `Bitacora` en la app `usuarios`. Es **inmutable** en dos niveles: el modelo rechaza `save()` sobre un registro existente y `delete()`, y un **trigger de Oracle** impide `UPDATE`/`DELETE` sobre la tabla. Solo lectura en el admin.

## Backend
- Dependencia nueva: `djangorestframework-simplejwt>=5.5`.
- App `usuarios`:
  - `roles.py`: constantes de los 4 roles.
  - `models.py`: `Bitacora(usuario FK null, fecha, accion, entidad, objeto_id, descripcion, valor_anterior JSON, valor_nuevo JSON, ip)`. Acciones: `LOGIN`, `LOGIN_FALLIDO`, `LOGOUT`, `CREAR`, `MODIFICAR`, `ELIMINAR`.
  - `services.py`: `registrar_evento(...)`, `roles_de(usuario)`, `tiene_rol(usuario, *roles)`, `datos_usuario(usuario)`.
  - `permissions.py`: `TieneRol` (fábrica de permisos DRF por rol).
  - Migraciones: creación de grupos (roles) y trigger de inmutabilidad.
  - Admin: alta/edición de usuarios registra `CREAR`/`MODIFICAR` en bitácora con valor anterior y nuevo (usuario, nombre, correo, activo, staff, roles). Bitácora en solo lectura.
  - Comando `crear_usuarios_demo`: un usuario por rol (solo con `DEBUG=True`).
- Endpoints:
  | Método | Ruta | Acceso | Descripción |
  |---|---|---|---|
  | POST | `/api/auth/login/` | público | `{username, password}` → `{access, refresh, usuario}`; registra `LOGIN` / `LOGIN_FALLIDO` |
  | POST | `/api/auth/refresh/` | público | `{refresh}` → nuevo par de tokens |
  | POST | `/api/auth/logout/` | autenticado | `{refresh}` → invalida el refresh; registra `LOGOUT` |
  | GET | `/api/auth/me/` | autenticado | datos y roles del usuario |
  | GET | `/api/bitacora/` | Auditor o superusuario | paginado; filtros `usuario`, `accion`, `desde`, `hasta` |
- Oracle: el usuario de la aplicación recibe los privilegios que Django necesita para crear la base de pruebas (`docker/oracle-init/01_privilegios_pruebas.sql`, se ejecuta al crear el volumen).

## Frontend
- `react-router-dom` para rutas: `/login`, `/` (inicio) y `/bitacora` (solo Auditor).
- Contexto de autenticación con tokens en `localStorage`, refresco automático del access al recibir 401 y cierre de sesión.
- Navbar con usuario, roles y botón "Cerrar sesión"; enlace a Bitácora solo para Auditor.

## Pruebas (`manage.py test usuarios`)
- Login correcto devuelve tokens y roles; login fallido devuelve 401; ambos quedan en bitácora.
- Endpoint protegido sin token → 401.
- Bitácora: Auditor → 200; Contador → 403.
- Logout invalida el refresh (refrescar después → 401).
- Bitácora inmutable: modificar o borrar un registro falla en el modelo **y** en la base de datos (trigger).
