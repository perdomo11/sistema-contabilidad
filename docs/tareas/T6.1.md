# T6.1: Pruebas, respaldos y manuales

## Objetivo
Cierre del proyecto (Bloque 6). Asegurar que el sistema funciona como un todo, que su información se puede respaldar y recuperar, y que usuarios y técnicos tienen la documentación para operarlo. Responde a la hipótesis del documento base (reducir errores frente a los procesos manuales) con evidencia verificable: cada regla contable tiene su prueba y el estado de la base se puede auditar en cualquier momento.

## 1. Pruebas
- **Prueba de integración de punta a punta** (`backend/config/tests_integracion.py`): con los datos de ejemplo (`cargar_catalogo_base`, `cargar_centros_base`, `cargar_asignacion_base`, `cargar_prorrateo_base`, `cargar_flujo_base`) recorre un ciclo completo: asientos de ingresos y gastos (directos y por regla), prorrateo, factura por pagar y su pago, presupuesto aprobado y distribuido. Verifica que los módulos cuadran entre sí:
  - balanza: cargos = abonos;
  - estado de resultados (T3.1) = resultado de la balanza; enfoque de contribución (T3.2) e indicadores (T3.3) = absorbente;
  - ejecución presupuestaria (T4.3) = gastos directos del estado de resultados;
  - flujo de efectivo real (T5.3) cuadra con el saldo contable; el dashboard (T5.4) coincide con sus fuentes;
  - `verificar_integridad` no encuentra fallas.
- **Comando `verificar_integridad`** (`python manage.py verificar_integridad [--anio]`): revisa las reglas sobre la base real y termina con código 1 si alguna falla, para usarlo antes de un cierre o después de restaurar un respaldo:
  1. Partida doble en todo asiento contabilizado (cargos = abonos = totales del encabezado).
  2. Líneas de resultado sin centro de costo (advertencia: solo admitidas en asientos anteriores a T2.1).
  3. Asientos de prorrateo vigentes contabilizados y con trazabilidad (`linea_origen`).
  4. Cuentas por pagar: saldo = total − pagos vigentes; estado coherente; anuladas con su reversión.
  5. Presupuesto: monto = última versión; Σ asignaciones ≤ institucional; Σ detalle ≤ asignación.
  6. Estado de resultados del ejercicio = resultado de la balanza.
  7. Bitácora: sin huecos de inmutabilidad (el trigger existe).
- **Matriz de pruebas** (`docs/PRUEBAS.md`): cada regla contable no negociable de `CLAUDE.md` → pruebas de servicio y de base de datos que la cubren; cómo ejecutar la suite y el resumen por módulo.

## 2. Respaldos (Oracle Data Pump)
Scripts en `scripts/` (Bash; en Windows se ejecutan con Git Bash):

| Script | Qué hace |
|---|---|
| `respaldo.sh` | `expdp` del esquema de la aplicación (tablas, datos, secuencias, triggers) dentro del contenedor y copia el `.dmp` y su log a `respaldos/AAAAMMDD_HHMMSS/` |
| `verificar_respaldo.sh <carpeta>` | Importa el respaldo en un **esquema temporal** (`REMAP_SCHEMA`), compara el número de filas por tabla con el esquema actual y borra el temporal. No toca los datos reales. |
| `restaurar.sh <carpeta>` | Pide confirmación escribiendo el nombre del esquema, detiene el backend, borra el esquema, lo importa del respaldo y vuelve a levantar el backend. |

`respaldos/` queda fuera de git. Las contraseñas se leen de `.env`.

## 3. Manuales
- `docs/MANUAL_USUARIO.md`: acceso y roles; un capítulo por módulo (catálogo, periodos, asientos, libros, centros de costo, asignación, prorrateo, reportes, presupuesto, tesorería, bitácora) con pasos, reglas que aplica el sistema y mensajes frecuentes; ciclos de trabajo (cierre mensual, ciclo presupuestario, ciclo de tesorería).
- `docs/MANUAL_TECNICO.md`: arquitectura, instalación y configuración (`.env`), estructura del código y convenciones, reglas en la base de datos (restricciones y triggers), API por módulo, comandos de carga de ejemplo, pruebas, respaldos y restauración, solución de problemas.
- `README.md` enlaza ambos manuales y los scripts.

## Checklist de validación
- [ ] `docker compose exec backend python manage.py test` pasa todo (incluida la integración)
- [ ] `docker compose exec backend python manage.py verificar_integridad` muestra todas las verificaciones en OK sobre la base de desarrollo
- [ ] `bash scripts/respaldo.sh` crea `respaldos/<fecha>/` con el `.dmp` y el log sin errores
- [ ] `bash scripts/verificar_respaldo.sh respaldos/<fecha>` informa las mismas filas por tabla y borra el esquema temporal
- [ ] (Opcional, en un entorno de prueba) `bash scripts/restaurar.sh respaldos/<fecha>` restaura y la aplicación vuelve a funcionar
- [ ] Revisar `docs/MANUAL_USUARIO.md`, `docs/MANUAL_TECNICO.md` y `docs/PRUEBAS.md`
